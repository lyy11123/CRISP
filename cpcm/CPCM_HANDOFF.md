# CPCM 交接说明：实现方案与验证步骤

2026-11-03 起草，同日按用户审阅意见修订（第 0、2、3、6 节）。判定关口已结束，模块定位见 `CLAUDE.md` 与方案文档中“判定关口结论与模块定稿”一节。

本说明只覆盖 CPCM 本身：实现、验证、耗时测量。把 CPCM 接进 SA、DSTU、EIR 是后续各自的交接说明，不在这里做。

## 0. 目标与定位

给定一个映射（事件图 + 路由 + 平台，可含故障），CPCM 用确定性的事件级列表调度算出每个事件的开始与结束时间，同时构建扩展依赖图：数据依赖边，加上 CPCM 自己调度出的资源服务顺序边。它给出以下输出：

| 输出 | 计算方式 | 后续用途 |
|---|---|---|
| 估计延迟 T̂ = max F(e) | 正向列表调度 | SA 能量、EIR 每级评估 |
| 关键路径 CP、各事件的等待 W(e)、LST 与 slack | 扩展图上的反向遍历 | 定位瓶颈；SA 的靶向移动 |
| 资源关键阻塞时间 CB(ρ) 与阻塞份额 φ(b, e) | 关键事件在资源上的等待，以及与等待区间重叠的服务事件 | 选改路链路；DSTU 候选 |
| 数据截止时间 D(b) | b 的数据后继中最小的 LST，不经过 b 自己发出的资源顺序边 | DSTU 的优先级键；判断改路是否可行 |

**贡献成立的条件**：CPCM 要落在“聚合代价”与“后端模拟”之间的保真度–成本前沿上（方案文档 ①“定位”）。具体是三条：
- 排序保真度明显高于聚合代价。E1 测得聚合代价的 τ 在 −0.49 到 0.66。
- 耗时明显低于后端。后端单算子 0.7–8 s，多流 17–150 s。
- 能做增量更新。

**论文定位（2026-11-03 审阅意见，本说明不实现）**：只拿 T̂ 当标量替换 SA 能量，会被看成“把模拟器改成确定性版本再加增量重算”。创新在于用归因量去改造搜索动作本身，这就要求本步把 CP、W(e)、CB(ρ)、D(b) 都做成可直接调用、经过验证的接口。后续用途有三处：
- **SA 关键路径靶向移动**：以较高概率挑 CP 上 W(e) 最大的事件所属算子做迁移，而不是随机挑。
- **改路链路的选取**：按 CB(ρ) 最大来挑，而不是按累计负载最大。依据是 E3：最忙的链路不一定关键。BusyBarn 和 TEMP 中按负载选链路的具体算法（文中称 BALD、TCME），引用前要对照原文核实。
- **DSTU 时空解阻**：先尝试空间改路，条件是 b 改走备选路径后预计完成时间 F′(b) ≤ D(b)；无解时再退回切块，并按 D(b) 逐跳仲裁。

## 1. 已知事实（来自 E0–E4，执行前不必重查）

- **事件规模**（E2 扩展的 summary 与 E3、E4 PROGRESS）：
  - GPT decode 单算子 631–710 个事件，例如 MHA 512 有 144 个计算、563 个通信。
  - OPT prefill：FFN 661 个，MHA 2,879 个。
  - Qwen3-MoE decode：FFN、MHA 各 4,782 个。
  - 三流约 2,000 个；切块后更多。
- **工况覆盖**（未被掩盖的纯通信占总延迟的比例，E2 扩展）：

  | 任务 | 纯通信占比 | 工况 |
  |---|---|---|
  | OPT prefill FFN | 0.02 | 计算主导 |
  | GPT decode | 0.23–0.39 | 均衡 |
  | Qwen3-MoE decode FFN | 0.87 | 通信主导 |

- **后端语义**（`src/backend/analytical/event_driver.py`，CLAUDE.md 与 E4a 已核实）：
  - 设备与链路一次只服务一个事件。
  - 多跳不是存储转发：同一 tick 发放所有空闲跳，已发放的跳继续占用（hold-and-wait）。
  - Phase 4 先 shuffle，再按剩余路径长度降序、按长度分层发放。
  - 某跳忙时只看剩余分支的第一跳，事件推迟到该链路的 work_endtime。
  - 计算事件不经过 Phase 4。
- **时长**：直接调用 artifact 的函数，不重抄常数。
  - 计算：`modules_dict[dev][loc].working_time(...)`。
  - 链路：`links_dict[path].working_time(...)`。
  - 调用点约在第 114、194 行；第 359/441、607 行是另外两个版本的同名调用。
  - 先核实这些函数是否只依赖大小等静态量；若依赖运行状态，先停下汇报。
- **后端的随机性与地址依赖**：
  - 换种子，总延迟平均波动约 1%、最大约 8%。
  - 同一状态、同一种子，换一个进程结果也会变，MHA 最多差 3.9%。
  - E4 中还出现过同一配置、不同种子落在两个离散结果上的情况。
  - 因此保真度一律与“后端多种子均值”比较，并同时报告后端自身的种子间波动作为噪声上限。
- **可复用代码**：
  - `e3_warmstart\e3_warmstart.py`：捕获并恢复映射（源、路由、tag、事件顺序），注入故障。
  - `e2_attribution\e2_attribution.py` 的 `Sim`：由后端记录建活动级图、关键链、阻塞归因。CPCM 用同样的图结构，输入换成自己的调度。
  - `e4_overlap\e4_backend*.py`、`e4b_backend.py`：多流合并、按跳仲裁、切块。
  - `e4b.py`：单流参照图上的 R̂ᵢ 与 tailₑ（理想值，验证 D(b) 时作对照）。

## 2. 实现方案

文件放在 `cpcm\`：`cpcm.py` 是核心库，`cpcm_v*.py` 是各验证脚本，输出写到 `cpcm_out\`。

1. **输入编译成扁平数组**
   - 从 `build_event` 之后的 `events_dict` 和平台对象中抽取图，一次性编译成扁平的整数索引数组：
     - 事件按静态拓扑序编号；
     - 依赖用 CSR 形式存储；
     - 每个通信的逐跳链路编号与时长；
     - 计算资源编号与时长；
     - 资源表（故障已删除）。
   - 推演的内层循环里不创建 Python 对象，不查复杂字典，不碰 artifact 对象。
   - 编译结果可缓存。SA 移动只改少数事件的资源、路由和时长字段。
2. **正向调度，两种模式，接口相同**
   - `bb`：复现 BusyBarn Phase 1–4 的规则，包括长度分层、同 tick 发放所有空闲跳、hold-and-wait、推迟到 work_endtime。原后端的随机 shuffle 换成确定性平局规则：按 (剩余长度, 事件整数编号) 字典序。
   - `hop`：按跳仲裁。优先级键是外部传入的数组，推演过程中不改变。这样做避免循环依赖：D(b) 要等正向推演和反向遍历都完成后才算得出。用法分两遍：
     1. 第 1 遍用 `bb` 模式（或无竞争、FIFO 的默认顺序）跑完正向推演和反向遍历，得到 LST⁽⁰⁾、CB⁽⁰⁾(ρ)、D⁽⁰⁾(b) 和 tailₑ。
     2. 第 2 遍用 `hop` 模式，把 D⁽⁰⁾(b) 或其他静态键作为固定输入。
     - 是否需要迭代多遍，作为验证项报告，不作为默认。
   - 实现方式：资源空闲时刻表加就绪堆。不要照搬后端“每发一跳就重排整个就绪表”的做法，那是后端超线性耗时的来源。
3. **反向遍历**
   - 在扩展图上算 LST、slack、W(e)、CP、CB(ρ)、φ(b, e)、D(b)。
   - 对外提供 `critical_path()`、`wait(e)`、`blocking(ρ)`、`deadline(b)`。
4. **单消息改路评估**
   - 接口：给定消息 b 和备选路径 π′，返回改路后的 T̂、F′(b)，以及 F′(b) ≤ D(b) 是否成立。
   - 内部走第 5 项的增量路径。DSTU 的空间改路和 EIR 的 L1 修复都会用到它。
5. **增量更新**
   - 输入：改动过的事件集合。
   - 从这些事件中最早的旧就绪时刻开始，按开始时间重算。当某事件的 S、F 和所在资源队列状态都与旧值一致时截断。
   - 截断后的结果必须与全量重算逐事件相同。
   - 网格争用下，早期改动可能让后续所有时间戳整体平移，截断条件因此很少触发，增量退化为全量。所以全量推演本身必须足够快（见 V7），增量只算锦上添花。截断率作为 V7 的一个报告项。
6. **多流**
   - 复用 E4 的合并方式：tag 第 1 位 = 10 + 流号，释放时刻 rᵢ。
   - 截止时间由 D(b) 按流聚合得到，不再用单流参照图的理想值。

## 3. 验证步骤与自检

每步完成后在 `cpcm\PROGRESS.md` 末尾追加一条，提交并推送，然后停下汇报数字。

**V0 手工小图**
- 内容：方案文档 ② 的两个动机例子，再加 3–5 个构造图，覆盖多跳、组播、hold-and-wait。
- 判据：CPCM 与手算结果逐事件相同。
- 不通过：停下。

**V1 语义回放**
- 内容：把后端记录的服务顺序强加给 CPCM。映射是 GPT decode 2048、2×2 的 FFN 和 MHA 胜出映射，再加 Qwen3-MoE decode FFN 一个。
- 判据：每个事件的 S、F 与后端记录逐个相同，不一致数为 0。
- 不通过：停下，报告第一处不一致和对应的源码行。

**V2 自主调度误差**
- 内容：在 V1 的映射之外，再加 1×4 和 OPT prefill 各一个；每个映射再配 E3 的 5 个故障。CPCM 用 `bb` 模式，与后端 5 个种子的均值比较。
- 报告：
  - \|T̂ − 均值\| / 均值；
  - 后端种子间的波动与 [min, max] 区间；
  - 按工况（计算主导、均衡、通信主导）分组的结果。
- 停止条件：误差中位数超过 3%，或最大值超过 10%，停下。
- 豁免：误差超过 10% 的单个点，如果后端在该点的多种子结果明显分成两团，而 CPCM 落在后端多种子的 [min, max] 内，或离边界不超过 3%，这个点不算失败，但单独列出。中位数判据不适用豁免。
- 不通过：停下问。

**V3 排序保真度**
- 内容：每个任务取 50–100 个映射，来自 SA 轨迹上的状态，做法同 E1。比较 CPCM 与后端均值的 Kendall τ。
- 报告：在同一批样本上同时给出三个 τ：
  - 聚合代价的 τ；
  - 后端两组种子之间的 τ，作为噪声上限；
  - CPCM 的 τ。
- 停止条件：CPCM 的 τ 不高于聚合代价时，停下。
- 不通过：停下问，因为这意味着 CPCM 作为贡献的主张不成立。

**V4 故障**
- 内容：E3 的 44 个“任务 × 故障”组合，各取 R0 和 FULL 两个映射。
- 报告：
  - 误差指标同 V2；
  - 再选 5 个故障，每个取 30–50 个故障后的候选映射，算 Kendall τ；
  - 结果按故障类型分组：节点、D2D、关键链路、DDR 端口、只坏 PE。
- 不通过：记录，不停。

**V5 多流与 `hop` 模式**
- 内容：E4b 设定 1 的 a1、a2 配置。
- 报告：
  - 两遍法的 T̂ 与 e4b 后端的误差；
  - D⁽⁰⁾(b)、R̂ᵢ 与 E4b 理想值之差；
  - 多迭代一遍后结果是否变化。
- 不通过：记录，不停。

**V6 归因一致性**
- 内容：在 V2 的映射上，把 CPCM 的 CP 和 CB(ρ) 与 E2 在后端记录上算出的关键链、阻塞归因对照。
- 报告：
  - 关键资源的重合率；
  - 前 3 个 CB(ρ) 资源是否相同；
  - “最忙链路 ≠ CB 最大链路”的配置数。
- 不通过：记录，不停。

**V7 耗时**
- 测量方式：串行、单进程。
- 测量项：
  - 单算子全量评估的耗时；
  - 1,000 次随机 SA 移动的增量评估耗时与截断率；
  - 单消息改路评估的耗时。
- 结果按事件数归一化报告，因为 MoE 有 4,782 个事件。
- 目标：约 700 个事件的单算子全量评估 10–30 ms。
- 先问的情况：超过 50 ms，或增量没有比全量快。
