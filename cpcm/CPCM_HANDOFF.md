# CPCM 交接说明：实现方案与验证步骤（草案，待用户确认）

2026-11-03 起草。判定关口已结束，模块定位见 `CLAUDE.md` 与方案文档“判定关口结论与模块定稿”。本说明只覆盖 CPCM 本身：实现、验证、耗时测量。把 CPCM 接进 SA、DSTU、EIR 是后续各自的交接说明，不在这里做。

## 0. 目标与定位

CPCM 在给定映射（事件图 + 路由 + 平台，可含故障）上，用确定性的事件级列表调度算出每个事件的开始与结束时间，并由此给出三类输出：

| 输出 | 计算方式 | 后续用途 |
|---|---|---|
| 估计延迟 T̂ = max F(e) | 正向列表调度 | SA 能量、EIR 每级评估 |
| 关键路径、LST 与 slack | 扩展图（数据依赖边 + CPCM 自己调度出的资源顺序边）上的反向遍历 | 归因、EIR 定位 |
| 数据截止时间 D(b) | b 的数据后继中最小的 LST，不经过 b 自己发出的资源顺序边 | DSTU 的优先级键 |

贡献成立的条件（方案文档 ① “定位”）：在“聚合代价”与“后端模拟”之间的保真度–成本前沿上。具体是：排序保真度明显高于聚合代价（E1：τ 在 −0.49 到 0.66），耗时明显低于后端（单算子 0.7–8 s，多流 17–150 s），且能增量更新。

## 1. 已知事实（来自 E0–E4，执行前不必重查）

- **事件规模**：单算子约 630–710 个事件，例如 MHA 512 有 144 个计算、563 个通信；三流约 2,000 个；切块后更多（E3、E4 PROGRESS）。
- **后端语义**（`src/backend/analytical/event_driver.py`，CLAUDE.md 与 E4a 已核实）：
  - 设备与链路一次只服务一个事件。
  - 多跳不是存储转发：空闲的各跳同一 tick 发放，已发放的跳继续占用（hold-and-wait）。
  - Phase 4 先 shuffle，再按剩余路径长度降序、按长度分层发放。
  - 某跳忙时，只看剩余分支的第一跳，事件推迟到该链路的 work_endtime。
  - 计算事件不经过 Phase 4。
- **时长**：计算取 `modules_dict[dev][loc].working_time(...)`，链路取 `links_dict[path].working_time(...)`（约第 114、194 行；第 359/441、607 行是另外两个版本的同名调用）。CPCM 直接调用这些函数取时长，不重抄常数。
- **后端的随机性与地址依赖**：
  - 随机打破平局，换种子总延迟平均变化约 1%、最多约 8%。
  - 对象地址也会影响结果：同一状态、同一种子，换个进程，MHA 最多相差 3.9%。
  - 因此保真度一律与“后端多种子均值”比较，同时报后端自身的种子间波动作为噪声上限。
- **可复用代码**：
  - `e3_warmstart\e3_warmstart.py`：捕获并恢复映射（源、路由、tag、事件顺序），注入故障。
  - `e2_attribution\e2_attribution.py` 的 `Sim`：由后端记录建活动级图、关键链与归因。CPCM 用同样的图结构，但输入换成自己的调度结果。
  - `e4_overlap\e4_backend*.py`、`e4b_backend.py`：多流合并、按跳仲裁、切块。
  - `e4b.py`：单流参照图上的 R̂ᵢ、tailₑ（理想值，验证 D(b) 时作对照）。

## 2. 实现方案

文件放在 `cpcm\`：`cpcm.py` 为核心库，`cpcm_v*.py` 为各验证脚本，输出写到 `cpcm_out\`。

1. **输入适配**：从 `build_event` 之后的 `events_dict` 与平台对象抽取一份精简图，抽取后不再依赖 artifact 对象。
   - 事件：类型、依赖、计算资源（设备、位置）、通信分支路径（逐跳链路）、各跳时长、计算时长。
   - 平台：资源集合，故障已从中删除。
   - 抽取一次，缓存成 pickle。SA 移动只改少数事件的这些字段。
2. **正向调度，两种模式**：
   - `bb`：复现 BusyBarn Phase 1–4 的规则，包括按长度分层、同 tick 发放所有空闲跳、hold-and-wait、推迟到 work_endtime。随机 shuffle 换成按 tag 的确定性平局规则，作为默认。
   - `hop`：按跳仲裁，键由调用方给出，与 E4b 后端同义。
   - 实现上用资源空闲时刻表加就绪堆，避免后端“每发一跳就重排整个就绪表”的超线性开销。先写纯 Python；只有达不到耗时目标时才考虑 numba 或 C 扩展，并先问用户。
3. **反向遍历**：在扩展图上算 LST、slack、关键链和 D(b)，对外提供 `critical_chain()`、`deadline(b)`、`blocking(ρ)` 三个接口。
4. **增量更新**：输入是改动过的事件集合。从它们最早的旧就绪时刻开始，按开始时间重算；当某事件的 S、F 与所在资源队列状态都和旧值一致时截断。截断结果必须与全量重算逐事件相同。加速比只能实测。
5. **多流**：复用 E4 的合并方式（tag 第 1 位 = 10 + 流号，释放时刻 rᵢ）。截止时间由 D(b) 按流聚合，不再取单流参照图的理想值。

## 3. 验证步骤与自检

每步完成后在 `cpcm\PROGRESS.md` 末尾追加一条，然后停下汇报。

| 步 | 内容 | 自检与判据 | 不通过时 |
|---|---|---|---|
| V0 | 手工小图：方案文档 ② 的两个动机例子，再加 3–5 个覆盖多跳、组播、hold-and-wait 的构造图 | CPCM 结果与手算逐事件相同 | 停下 |
| V1 | 语义回放：在 GPT decode 2048、2×2 的 FFN、MHA 胜出映射上，把后端记录的服务顺序强加给 CPCM | 每个事件的 S、F 与后端记录逐个相同，不一致数为 0 | 停下，报告第一处不一致及对应源码行 |
| V2 | 自主调度误差：同上两个映射，加 1×4、prefill 各一个，每个再加 E3 的 5 个故障，CPCM `bb` 模式对后端 5 个种子的均值 | 报告 \|T̂ − 均值\| / 均值，并与后端种子间波动对照；中位数超过 3% 或最大值超过 10% 时停下 | 停下问 |
| V3 | 排序保真度：每个任务取 50–100 个映射（SA 轨迹上的状态，做法同 E1），比较 CPCM 与后端均值的 Kendall τ | 同一样本上同时报：聚合代价的 τ、后端两组种子之间的 τ（噪声上限）、CPCM 的 τ；CPCM 的 τ 不高于聚合代价时停下 | 停下问：贡献主张不成立 |
| V4 | 故障：E3 的 44 个“任务 × 故障”组合，各取 R0 和 FULL 两个映射 | 指标同 V2；按故障类型（节点、D2D、关键链路、DDR 端口）分组报告 | 记录，不停 |
| V5 | 多流与 `hop` 模式：E4b 设定 1 的 a1、a2 配置 | 两项：T̂ 与 e4b 后端的误差；CPCM 的 D(b)、R̂ᵢ 与 E4b 理想值之差 | 记录，不停 |
| V6 | 输出一致性：V2 的映射上，CPCM 关键链与 E2 在后端记录上算出的关键链 | 关键资源的重合率；前 3 个关键资源是否相同 | 记录，不停 |
| V7 | 耗时：串行、单进程，单算子全量评估，以及 1,000 次随机 SA 移动的增量评估 | 报告毫秒数与相对后端的比例；单算子全量超过 50 ms，或增量没有快于全量时，先问 | 先问 |

## 4. 记录与复现

- **记录**：artifact commit、随机种子、命令行、样本映射的来源（SA 轨迹的种子与步号）。
- **运行**：一个进程只跑一个任务脚本；会覆盖 `results\` 的部分在 `cpcm\work\` 的 artifact 工作副本里运行。
- **耗时**：单次运行预计超过 1 小时，先告诉用户。
- **提交**：开工前 pull，每完成一步提交并推送，按 README 的协作约定。
