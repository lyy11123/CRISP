# C：GPT 同一物理故障（W1）运行方案（草案）

2026-11-09，只读起草：没有写代码，没有跑任何运行。用户放行后才动手（`E2E_HANDOFF.md` 第 4 节末尾“下一步 C”）。

- 耗时标“估”的都是推算：以 B4 的单次墙钟（本机 12–14 个并行，含争用）和 EIR 的已有记录折算，未实测。
- Colab 按 B4 的验证折算：7 个并行时，单次约为本机的 1.25–1.45 倍。

## 1. 问题

一个物理故障同时作用在一层的全部算子上，即 prefill 和 decode 的 LN、MHA、投影、FFN，共 8 个。比较两种做法的端到端延迟（TTFT、TPOT、请求延迟）、迁移量和修复步数：

- BusyBarn 起点 + BusyBarn 的修复：R0、FULL-BusyBarn。
- A3h 起点 + EIR 主力修复与 FULL。

## 2. 配置

- **模型与平台：** GPT，序列 2048，2×2 组，W1，共享 KV 口径（B4）。
- **算子：** 8 个，均按 B4 的 W1 起点，每个算子单独映射在同一个 2×2 组上。
- **故障作用方式：** 一个故障坐标同时加到 8 个算子的平台上，每个算子分别修复，再按 B4 的方式组装。
- **组装：** 同 B4。T_block = 2·LN + 8·MHA + 投影 + FFN；TTFT = prefill T_block；TPOT = decode T_block（KV 长度 2048 的近似）；请求延迟 = TTFT + 输出长度 × TPOT，输出长度取 128、512、2048。
- **LN 计数：** 原样与修正两份并列，同 B4。

## 3. 故障类别

沿用 EIR 的类别：

| 类别 | EIR 编号 | 说明 |
|---|---|---|
| 节点（核 + 路由器） | F1、F2 | 角落核（0、3、12、15）不能失效（artifact 抛 ValueError） |
| D2D 链路，双向 | F4 | |
| 片内链路，双向 | F5 | |
| 只坏 PE，路由器仍转发 | F6、F7 | |
| DDR 端口节点 | F8 | |
| k = 4 复合 | CRandom、CCluster、CEdge、CScratch | |

共 11 个故障。可以减少，见第 8 节的问题 2。

## 4. 坐标怎么选

8 个算子各有自己的映射，所以“关键链路”“最忙核”对每个算子不同。三种做法：

| 做法 | 内容 | 利 | 弊 |
|---|---|---|---|
| (a) 按物理规则固定 | 只看拓扑，不看映射：例如每类取几处位置，如中间的 D2D 对、非角落的中心核、某个 DDR 端口，事先列出，8 个算子与两个起点共用 | 与任何映射无关，A1 与 A3h 两个起点公平；可复现；论文里好描述 | 对某些算子可能落在轻载资源上，故障代价小、噪声相对大；不针对关键路径，难以体现“关键链路坏了”的情形 |
| (b) 按某个算子的映射选 | 用 EIR 的原规则（最忙链路、关键链路、最忙 DDR 端口等）在一个算子的映射上选，例如请求延迟的主项 decode MHA，或 TTFT 的主项 prefill MHA | 与 EIR 一脉相承，规则现成（`eir.select`、`eir_next.choose_c`）；至少一个算子确实受压 | 在哪个起点上选就偏向哪个起点（在 A3h 上选对 A3h 更苛刻，在 A1 上选反之）；其余 7 个算子可能几乎不受影响 |
| (c) 按全部算子加权选（新规则） | 对每个候选位置，按“各算子上该资源的忙碌量 × 该算子在请求延迟中的占比”求和，在 A1 与 A3h 两个起点上各算一次再相加，取最大者 | 代表整条请求受到的冲击；对两个起点对称 | 是新规则，不是 EIR 原规则，要先写进 PROGRESS；占比与输出长度有关（128 与 2048 的权重不同），要先定按哪个输出长度 |

## 5. 起点与修复

| 起点 | 修复 | 内容 |
|---|---|---|
| A1（BusyBarn） | R0 | 只改路由（l1 作业里的 R0），记录修复前的故障后延迟 |
| A1 | FULL-BusyBarn | 14 个 A1 变体在故障平台上重跑模板，按模板规则取胜者 |
| A3h | R0 | 同上（l1 作业附带，不另计） |
| A3h | EIR 主力修复 | L2-Global（+sync），步数档 30、100、300，ε = 2% 停止规则逐级升级，5 个种子（EIR 主实验口径） |
| A3h | FULL | A3h 14 个试验配置在故障平台上重搜（`cpcm_sa` 第 2 阶段规则，1000 步） |

**起点选法**（第 8 节的问题 3）：

- A3h：每个算子取 B4 W1 的后端最优。
- A1 有两种取法：
  - B4 的后端最优；
  - 模板规则，即模板自己的最终评估最小者，EIR 的 E3 组 2026-11-09 已改用这种。

## 6. 指标

| 指标 | 内容 |
|---|---|
| 延迟 | TTFT、TPOT，请求延迟（输出 128、512、2048）。每个“起点 × 修复”报故障前、R0、修复后、FULL，相对故障前和相对 A1 故障前；各算子的三元组与通信占比 |
| 迁移量 | 每个算子搬动的行为占比和权重字节，按层求和（EIR 口径） |
| 修复步数 | 停在哪一级（R0 / L1 / L2 的步数档 / FULL），所用 SA 步数，各算子与合计 |
| 其他 | T̂ 对后端误差、后端噪声（同 B4） |

## 8. 需要用户定的问题

1. **坐标选法：** (a)、(b)、(c) 中选哪个。若选 (b)，按哪个算子、在哪个起点上选。若选 (c)，按哪个输出长度加权。
2. **故障集合：** 11 个全跑，还是减少（例如 7 个单点，或每类 1 个）。
3. **A1 起点：** 每个算子用 B4 的后端最优，还是模板规则（与 EIR 的 E3 组一致）。
4. **步数档：** 3 档全跑，还是按 ε 规则分段跑。分段跑省时，但要分轮。
5. **FULL-A3h：** 每个算子 14 个全跑（占比最大），还是减少。
6. **单进程 1 小时停线：** 对 prefill MHA、LN 的 300 步修复和 FULL 是否放宽，例如放到 2 小时。
7. **代码范围：** EIR 现有代码只覆盖 GPT decode 的 MHA、FFN 任务。C 需要在 `e2e\` 写新代码，接入 prefill 模型和 LN、投影（不改 `eir\`）。放行后先做冒烟和与 EIR decode 结果的逐位回归。
8. **故障的时间语义：** 默认故障在请求开始前已发生，修复完成后再服务请求。B4 不含请求中途故障，若要在请求中途发生，需另定窗口口径（EIR 阶段 B 的时间轴）。
