## 0. 目标与阶段

E4 检验 DSTU 的前提：**几条数据流在同一组 Die 上重叠执行时，共享链路（D2D、DDR 出口、片内要道）上的冲突是否足够大，按 slack 排序是否值得做。**

收益只能来自各条流 slack 的差异。slack = 截止时间 − 当前时刻 − 剩余工作；差异有三个来源：截止时间不同、剩余工作不同（所处阶段不同，或 token 数不同）、到达时间不同。同一算子、同一长度的几个 micro-batch 只剩“到达时间”一项差异，按 slack 排序会退化为先到先服务，所以必须设置不对称的场景，并以对称场景作对照。E2 的单算子重排收益 ≤ 3.4%，原因正是一个算子内部各传输的剩余工作差别很小；E4 用跨流、跨阶段的差异来检验收益。

| 阶段 | 内容 | 本说明是否覆盖 |

| **E4a 测量与判定** | 合并多条流的事件图、加释放时间，链路仲裁保持 BusyBarn 默认；用 E2 的分析流程算跨流的收益上限（以最大放大倍数为目标，见 3.3）；含故障场景 | **是** |

**E4a 只做测量，不实现任何仲裁策略。**

## 2. 与 E4 相关的源码事实（我读源码所得，请先核实）

- 后端 `event_driver`（`src/backend/analytical/event_driver.py`）：没有依赖的事件一律在时刻 0 开始（约第 296–301 行），**没有释放时间的概念**。链路仲裁在“Phase 4”：每个时刻把就绪的通信 `random.shuffle` 后按 `max(len(路径))` 降序排序，路径长的先发；设备被占用时计算事件推迟到 `work_endtime`。每条链路一次传完整条消息，占用时间 = `ceil(ceil(bytes/bandwidth)·timeunit) + latency`。**注意：BusyBarn 默认仲裁是“随机打乱后路径长的先发”，不是先到先服务**；E4a 的收益空间都是相对这个默认规则而言。
- 事件 tag（2026-11-01 在 E3 捕获的模板事件图上核实，FFN/MHA，2×2 与 1×4）：计算 tag 是 5 元组，例如 `(0, 0, 0, 0, 0)`；通信 tag 是 6 元组，例如 `(1, 0, 0, 4, 1, 3)`。第 0 位 0 = 计算、1 = 通信；第 1、2 位恒为 0；第 3 位是算子序号；第 4 位是分块序号；通信 tag 的最后一位是编号。映射按第 2 位查候选设备（`Pre_Mapping.py` 第 218 行、`Stream_Mapping.py` 第 614 行、`mapping.py` 第 109/216 行，这一位不能改）。后端把第 1 位当作 prefill/decode 标志：某个计算事件 `tag[1] == 1` 变为就绪时打印 `prefill time cost`（`event_driver.py` 第 345 行，只打印，不影响仿真）。合并多条流时，把流编号放在第 1 位，取值 **10 + 流号**（避开 1），保持第 0 位和“通信 tag 可由 tag[1:-1] 找到所属计算事件”这一关系。E4c 做 PD 共置时第 1 位可能要留给它原本的用途，届时再定。
- 映射代码里没有 SRAM 容量约束（`src/mapping` 中搜不到 capacity / sram）。几条流叠在同一组 Die 上，权重与 KV（含 8192）不检查能否放下。E4a 把这作为明确的假设写进汇总，不处理。
- decode MHA 在三种 KV 长度下的胜出变体（E2 的结果，2×2）：512 → `greedy0_lossratio0`（16,259），2048 → `greedy0_lossratio4`（20,153），8192 → `greedy0_lossratio5`（38,608）。decode FFN 用 `greedy0_lossratio6`（203,603），它与序列长度无关。**请核实这些就是 14 个变体中总延迟最小者**；若不是，以核实结果为准并记录。
- 评估器有跨进程噪声（同一状态、同一种子最多相差约 4%，见 CLAUDE.md），比较时用多个种子的均值。

## 3. 方法定义

### 3.1 流的组成

| 组成 | 不对称从哪来 | 2 条流 | 3 条流 | 对称对照 |
|---|---|---|---|---|
| a1 | KV 长度不同 | 2 个 decode MHA，KV 长度 (512, 8192) 和 (2048, 8192) 两组 | 3 个 decode MHA，KV 长度 512、2048、8192 | 全部为 2048 |
| a2 | 所处阶段不同（层间流水） | 1 个 decode MHA + 1 个 decode FFN | MHA、FFN、MHA（流水线上相邻的三个 micro-batch） | 同算子、同长度（2 条流：两个 MHA 2048；3 条流：三个 MHA 2048） |

- 每条流使用**它自己单独映射得到的故障前最终映射**（第 2 节所列胜出变体，用 E3 的方法捕获，含源、路由、tag 与事件顺序），各流都映射到同一个 2×2 Die 组。这模拟“每条流各自映射、运行时共用硬件”。
- 平台只有一个；合并后的事件图在同一个平台上仿真。
- 释放时间的实现：二选一，在 PROGRESS 里记录所选方式。(a) 每条流加一个虚拟计算事件，放在一个不参与其他工作的虚拟设备上，时长 = 释放时间，该流所有无依赖的事件都依赖它；(b) 在内存中替换后端，让每条流的无依赖事件在释放时刻才进入就绪队列。用 (a) 时，E2 的关键链会把虚拟事件算成一段活动，归因、跨流阻塞占比和收益上限都必须排除它。

### 3.2 变化的维度

| 维度 | 取值 |
|---|---|
| 错开时间 Δ | 0、0.25T、0.5T、1T，T 为参与组合的各流中**最短**那条流单独运行的延迟（多种子均值）。第 i 条流的释放时间 = i × Δ。另跑“完全串行”作参照：第 i 条流在第 i−1 条流完成后释放。说明：a2 中 decode FFN（约 203,603）比 MHA（约 20,153）长约 10 倍，若按较长的流定义 T，0.25T 起短流就完全错开、不再重叠；按最短的流定义，四档对应短流与长流前段不同程度的重叠。另记录每个配置中各流实际重叠的时长 |
| 截止时间 | 每条流的截止时间 = 释放时间 + k × 该流单独运行的延迟，k ∈ {1.1, 1.5, 2.0}。只用于计算 slack 与满足率，不影响仿真 |
| 流数 | 2 与 3，每种组成、每种情况都做 |
| 硬件状态 | 无故障；F4（最忙的 D2D 链路，两个方向失效）；F5（关键等待最多的片内或 D2D 链路，两个方向失效）。F4、F5 在“合并后、Δ = 0、无故障”的那张图上按 E3 的同名规则选出；各流再按 E3 的 R0 规则（保留路由，只对被切断的通信重新选路）得到故障后的映射 |
| 消息切块 | 不切；切块（块大小见任务清单第 3 步）。切块 = 一条消息拆成若干同路径的通信事件，每块都依赖原来的生产者，消费者依赖全部块；块之间不互相依赖。每块都要付一次链路延迟，这部分开销要单独报告 |
| 拓扑 | 2×2 为主；1×4 只抽查（a1、a2 的 2 条流各一个非对称配置，Δ = 0.5T，无故障与 F4 各一次） |

核心网格：9 组流组合（a1：2 条流 3 组〔(512, 8192)、(2048, 8192)、对称〕，3 条流 2 组〔非对称、对称〕；a2：2 条流 2 组、3 条流 2 组〔非对称、对称〕）× 5 种错开（4 种 Δ + 串行）× 3 种硬件状态 × 2 种切块方式 = 270 个配置，每个配置 3 个后端种子，共 810 次评估；另加 1×4 抽查。

### 3.3 测量的量

记号：第 i 条流的释放时间 rᵢ、完成时间 Cᵢ、单独运行的延迟 Tᵢ（多种子均值）、截止时间 dᵢ = rᵢ + k·Tᵢ。

**主指标：最大放大倍数 S_max = maxᵢ (Cᵢ − rᵢ) / Tᵢ。** 它是调度理论中最大延误 L_max = maxᵢ (Cᵢ − dᵢ)（Graham 记号 `1|r_j|L_max`，Jackson 1955 的截止时间最早优先规则）在“截止时间正比于单独延迟”时去掉 k 的形式：所有流都满足截止时间 ⇔ S_max ≤ k，即 S_max 是让所有流都满足截止时间所需的最小 k。在调度文献中又称 maximum stretch / slowdown（Bender 等 1998，引用前需核对）。选它而不是满足率，是因为 E4a 只有 2–3 条流，满足率只能取几个离散值，作判定不够灵敏；E4c 再换成 LLM 服务文献通用的 SLO 满足率、goodput、P99，与静态分区对比。

对每个配置、每个种子：
- 每条流的完成时间、延迟（Cᵢ − rᵢ）、放大倍数 (Cᵢ − rᵢ)/Tᵢ；S_max；
- 整体完成时间，以及流水节拍 =（最后一条流完成 − 第一条流释放）/ 流数；
- 按每个 k ∈ {1.1, 1.5, 2.0} 的截止时间满足情况（可由 S_max 和各流放大倍数直接读出）；
- slack 差异指标：在各流**开始重叠的时刻** t（第 1 条之后每条流的释放时刻）计算每条已释放、未完成的流的 slack = dᵢ − t − 剩余工作ᵢ，剩余工作ᵢ 用该流单独运行时在 (t − rᵢ) 处尚未完成的部分估计（即 Tᵢ − (t − rᵢ)，下限 0）；报告各时刻 slack 的极差与变异系数（按 k 分别算）。对称、Δ = 0 时应为 0；
- 关键等待归因（E2 流程）：关键等待落在哪类资源（计算单元、片内链路、D2D、DDR 出口）；**跨流阻塞占比**：阻塞者与被阻塞者属于不同流的关键等待所占比例；
- **收益上限，以 S_max 为目标**（在合并后的事件图上，单资源）：对一个资源上排队的各个活动，给每个活动一个截止时间 = 所属流的 dᵢ − 该活动结束后到该流终点的最长剩余路径（剩余路径按原图计算，与 E2 的 tail 相同），在保持其他资源不变的前提下，求该资源上可达到的最小 S_max。S_max 是比值，不能由某一个 k 下的 L_max 直接换算（各流 Tᵢ 不同时，最优顺序随 k 变化），做法是对 k 二分：给定 k，用截止时间最早优先 / Jackson 规则与精确解判断该资源上是否存在 L_max ≤ 0 的顺序；最小的可行 k 即该资源上的最优 S_max。报告 S_max 的下降比例，取关键等待前 5 的资源中的最大值。另按 k ∈ {1.1, 1.5, 2.0} 分别报告各自的最小 L_max；
- 收益上限，以整体完成时间为目标（对照，与 E2、E3 定义相同）：单资源精确重排收益、删去单个资源的收益上限（取关键等待前 5 的资源中的最大值）。此时一个资源上排队的是来自不同流的传输。
- **流级优先级（执行前须经用户确认，默认不做）**：对 2 条流的 2 种、3 条流的 6 种优先级顺序，在内存中给 Phase 4 的排序加一个“流优先级”作为第一键（原有的路径长度为第二键），各跑一遍后端，报告最好顺序下的 S_max 与默认仲裁之比。它同时作用于所有资源，比单资源上限更接近实际可得的收益；但它改动了后端的排序规则，是否算 E4a 的测量由用户决定。

## 4. 必须通过的自检

写进汇总；任何一项不通过，就报错停止。

1. **单流复现**：只有 1 条流、释放时间 0 时，合并工具输出的事件图与该流原图同构（用 E3 的 `graph_diff`），且 3 个种子的平均延迟与原图的平均延迟相差不超过 1%。
2. **释放时间被遵守**：没有任何事件早于它所在流的释放时间开始；若用虚拟事件实现释放时间，确认它们已从归因与收益上限的计算中排除。
3. **串行参照**：完全串行时，每条流的延迟与它单独运行时的平均延迟相差不超过 1%（均值比较），并且没有跨流阻塞。
4. **切块守恒**：切块后每条消息的总字节数不变；块大小大于最大消息时，结果与不切块的图同构。
5. **E2 分析有效**：E2 `analyse` 内部的自检（关键链覆盖 [0, a]、活动图最长路径等于 a 等）在每张图上都通过。
6. **S_max 上限的一致性**：只有 1 条流时，以 S_max 为目标的单资源上限换算回总延迟，与 E2 以整体完成时间为目标的单资源精确重排结果一致（两者此时是同一个问题）。

## 7. 遇到这些情况先停下来问

- 合并后的事件图无法通过自检 1（单流复现）。
- tag 改名规则与第 2 节的描述不符，或合并后 BusyBarn 的某个函数依赖 tag 的其他位。
- 切块让单次评估慢到全网格预计超过 1 小时。
- 关键等待绝大部分落在计算单元而不是链路上（此时链路仲裁的前提不成立，先报告再决定）。
- 源码行为与第 2 节的描述不符。
- 单个进程运行超过 1 小时。

## 8. 讨论中已确定、留给后续阶段的要点（不在 E4a 中实现）

- slack 按 token 数估计：剩余工作 = 当前这一步余下的关键路径（CPCM）+ 由 token 数推算的后续各步；截止时间由 TTFT（prefill，可随输入长度放宽）与 TPOT（decode 每步）给出。输出长度事先未知，可只用每步 TPOT，或用输出长度预测（引用前需查文献）。长度与延迟的关系用 BusyBarn 的实测数据校准。
- 多维评估：prefill 长度、decode KV 长度、请求类别（Azure trace 的 code / conversation，分布需从 trace 统计核实）、阶段差、SLO 松紧、负载、故障状态；以“slack 差异 vs 收益”图统一呈现；每种策略面对同一组请求；SLO 要扫多档，不只挑一组。
- E4c 的 prefill 用 chunked prefill（块长 256 / 512），否则 prefill 的工作量会完全压倒 decode。BusyBarn 的 prefill 生成脚本（`models/intra_mapping_gpt_prefill/*.py`）是参数化的，可以生成任意长度。
- 论文叙事：DSTU 不与 FACE、DistServe 正面竞争调度，而是解决“重叠执行之后的链路级冲突”，故障后更严重；对照组必须包括静态分区；不在单算子平均延迟上比较。
